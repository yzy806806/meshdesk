# QUIC Disguise Feasibility Report for MeshDesk v2

Generated by researcher. Investigation target: quic-go source, GFW QUIC handling, self-implementation estimate.

---

## 1. Can quic-go be used to forge QUIC Short Headers?

**Answer: Yes, but only by copying code — the wire package is internal.**

quic-go's `internal/wire/short_header.go` (62 lines) exposes two functions:

```go
// AppendShortHeader writes a QUIC short header to a byte slice.
func AppendShortHeader(b []byte, connID protocol.ConnectionID, 
    pn protocol.PacketNumber, pnLen protocol.PacketNumberLen, 
    kp protocol.KeyPhaseBit) ([]byte, error)
```

This is a **pure function** — no state machine, no goroutines, no connection tracking. It takes a byte buffer and appends:
1. Type byte: `0x40 | uint8(pnLen-1)`  — fixed top bit 0, QUIC bit 1 set, reserved bits 0
2. Destination Connection ID bytes
3. Encoded packet number (1-4 bytes, big-endian)

The encoding is standard RFC 9000 and trivially verifiable:
- `protocol.ConnectionID`: byte slice wrapper (max 20 bytes)
- `protocol.PacketNumber`: int64 alias
- `protocol.PacketNumberLen`: uint8 alias (1-4)

**Problem**: quic-go's wire package is at `internal/wire` — NOT exported. `go get github.com/quic-go/quic-go` gives you the QUIC connection/transport layer, not packet encoding primitives. The `internal/` directory is Go's convention for unexportable packages.

**Workaround**: Copy the relevant ~100 lines from quic-go's `internal/wire/` and `internal/protocol/` into MeshDesk's `internal/transport/quicwire/` package. This is NOT a fork — it's extracting a well-specified wire format implementation (RFC 9000). The code is MIT-licensed and quic-go is a Go ecosystem standard library equivalent.

**Alternatively**: quic-go does expose some wire-level types via the `quicvarint` package. But short header encoding is fully internal.

## 2. Self-implementation code estimate — ~2000 lines is an overestimate

The actual code needed for QUIC packet encoding:

| Component | Code size | Source |
|---|---|---|
| Short Header (append + parse) | ~40 lines | quic-go wire/short_header.go |
| Long Header (append + parse) | ~80 lines | quic-go wire/extended_header.go |
| Packet Number encoding | ~20 lines | quic-go wire + protocol |
| QUIC varint encoding | ~50 lines | quic-go quicvarint/ |
| Connection ID type | ~15 lines | quic-go protocol |
| Header Protection (AES-ECB) | ~20 lines | RFC 9001 §5.4, trivial |
| Frame types (PING, PADDING, STREAM) | ~60 lines | Optional for disguise |

**Total: ~285 lines of wire format code**, plus ~200 lines of tests. A full QUIC transport layer (congestion control, flow control, ACKing, loss recovery) would be 5,000+ lines — but for disguise we only need the wire format, not the transport semantics.

**The ~2000-line figure is wrong** because it conflates QUIC transport protocol implementation with QUIC packet encoding. For disguise purposes, we only need:
1. Encode our data into a byte payload
2. Wrap it in a valid QUIC Short Header frame
3. Apply header protection (optional for disguise)
4. Send it as a UDP packet

The DPI sees: valid QUIC short header → opaque encrypted payload → indistinguishable from real QUIC application data.

## 3. GFW QUIC Detection: State Machine vs Pattern Matching

Based on public research (2024-2026):

**What GFW likely does:**
- **Version fingerprinting**: Inspects QUIC version field in Initial packets. Only v1 (0x00000001) and v2 (0x6b3343cf) are considered "real" QUIC.
- **DCID/SCID length patterns**: Chrome QUIC uses 8-byte DCID; custom lengths flagged as anomalous.
- **TLS 1.3 handshake inside Initial packets**: If the CRYPTO frame doesn't contain a valid TLS ClientHello with known SNI, it's flagged.
- **Traffic volume/pattern analysis**: A QUIC connection that never sends ACK frames or has unusual packet pacing is anomalous.

**What GFW likely does NOT do:**
- **Full QUIC state machine validation**: Tracking connection state, verifying ACK frames, checking flow control limits — this is computationally expensive at carrier scale.
- **Packet number decryption**: QUIC encrypts packet numbers; DPI would need active decryption which is protocol violation at scale.
- **Deep payload inspection of 1-RTT packets**: Short header packets are encrypted; DPI can't see the content.

**Key insight for MeshDesk's QUIC disguise:**

Since MeshDesk uses Reality (which handles the TLS 1.3 handshake with a real domain's certificate), the QUIC disguise layer only needs to handle:
1. **Initial packets**: Must have valid QUIC version, DCID length matching browser behavior, and contain a valid TLS 1.3 ClientHello with a real SNI. Reality already generates this for TCP — the same TLS handshake works inside QUIC CRYPTO frames.
2. **1-RTT packets**: Use Short Header format with random connection ID and incrementing packet number. These are encrypted and look identical to real QUIC application data.

**The challenge specific to QUIC disguise**: The TLS handshake must be embedded in QUIC CRYPTO frames (RFC 9001), not raw TLS records. This requires a framing shim that wraps TLS messages in QUIC frames. This is ~100 lines of additional code.

## 4. Conclusion and Recommendations

### QUIC disguise IS feasible, but with caveats:

1. **QUIC wire format encoding is ~285 lines** — not 2000. It's well-specified in RFC 9000 and trivially testable (generate a packet, verify quic-go can parse it).

2. **The hard part is NOT the wire format** — it's embedding the Reality TLS 1.3 handshake inside QUIC CRYPTO frames. This requires a CRYPTO frame encoder (~40 lines) and a coordinator that feeds TLS `Write()` output into CRYPTO frames sent as Initial/Handshake packets. This is ~200 lines total.

3. **quic-go's wire package is internal and cannot be imported directly.** The code must be copied into MeshDesk (MIT license, ~100 lines of RFC-mandated wire format — no IP concern).

4. **Initial packets are the DPI attack surface.** The QUIC Initial packet reveals the TLS SNI (in plaintext CRYPTO frames before handshake encryption). Reality's approach of using a real domain's certificate means the SNI IS a real domain — this is actually stronger for QUIC than for TCP because QUIC Initial packets are inherently harder to inspect at depth.

### Recommendation: Implement ~500 lines of QUIC wire format + CRYPTO frame shim. Defer to v2.1.

The QUIC disguise requires:
- `internal/transport/quicwire/` — QUIC packet encoding (~285 lines)
- `internal/transport/quic_crypto.go` — CRYPTO frame ↔ TLS bridge (~200 lines)
- Integration with Reality TLS transport (~50 lines hook)

This is ~500 lines, not 2000. However, the testing surface is large (interop with quic-go client, Chromium's QUIC stack) and the DPI risk of getting QUIC Initial packets wrong is high.

**Alternative if QUIC is deferred**: Use TCP + Reality TLS as the production transport (proven in v1, 841 lines already implemented). For UDP-based transport without QUIC disguise, KCP (github.com/xtaci/kcp-go) provides reliable UDP transport with congestion control — but KCP packets have a distinct 24-byte header that DPI can fingerprint. A custom UDP protocol with AES-GCM encrypted payload + random-length padding (no recognizable header) is simpler and harder to fingerprint than emulating QUIC.

**Priority**: Ship v2 with TCP + Reality TLS. Add QUIC disguise as a gated experimental transport (`transport.quic.enabled=false` default) in v2.1 after DPI testing against real GFW.
